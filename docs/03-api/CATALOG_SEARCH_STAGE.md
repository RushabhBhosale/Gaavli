# Master product directory: search foundation (incomplete)

This is a first stage of the requested directory, not a production-ready
replacement for Product Master. Existing seller listings and `productMasters`
remain unchanged. The Add Listing picker now uses the search endpoint with a
300 ms debounce and displays up to 20 matches. Offline and network-error search
uses matching products saved in the mobile reference cache. The picker does not
yet paginate results or incrementally sync the complete catalog.

`GET /api/v1/catalog/search?q=...&limit=10` requires a mobile session and
returns `{ products, didYouMean }`: the Product Master page DTO plus a corrected
spelling (or `null`). Input is limited to 80 characters, results to 20, and
requests to 240 per account per minute.

Matching, best first (each step is an indexed, bounded query; no scans):

1. Whole phrase: exact name, exact alias, then phrase prefix.
2. Word by word, in any order (up to four words): every word of every name and
   alias is indexed on its own. A word matches exactly, by prefix (the word
   still being typed), by sound, or as a typo. Products matching all words rank
   first; a product matching at least half the words, including the most
   distinctive one, may follow as a close match.
3. Sound: romanized Marathi/Hindi spellings (kothimbir, kothambir, kothimbeer;
   aloo, alu) and Devanagari variants (ि/ी, श/ष/स, ण/न) share an indexed
   spelling-neutral `key`, and an indexed consonant skeleton `skel` covers
   missing or swapped vowels.
4. Typos: swapped neighbouring letters, and edit distance (insert, delete,
   substitute, swap) of 0 for words up to 3 characters, 1 up to 6, and 2 beyond.
   Candidates come from indexed deletion keys; terms under 4 characters are
   never typo targets, so short words do not match unrelated ones.

`didYouMean` is set only when the best result needed a guess (sound or typo),
for example `tomtao` -> `tomato`, `tomato ketchap` -> `tomato ketchup`.
Results are read back from the master so inactive or deleted records cannot be
selected through stale index entries. Each candidate query is capped at 100 and
has a one-second database execution limit; a word with more candidates than the
cap is re-checked by product id so a common word cannot hide a real match.
Typo and sound matches are lookup aids only: every candidate is verified in
code before it is ranked. The offline fallback in the mobile app uses the same
edit-distance helper (`@gaavli/utils`) and word-order-independent matching over
cached products. No load test has been run; single-search latency was measured
only from a development machine, where one Atlas round trip is about 100 ms and
a search takes two to three round trips.

To prepare the index for an existing database, run from the repository root:

```sh
npm run index:catalog-search --workspace=@gaavli/web
npm run index:catalog-search --workspace=@gaavli/web -- --apply
```

The first command is a read-only dry run. The second creates the search indexes
and idempotently upserts terms (names, aliases, each word, plus the sound keys)
for current master products, then removes terms no longer produced; it does not
modify listings or master products. Re-run after changing master names or the alias
file: index maintenance is not yet automatic and cached results are not used.
Run only after checking the configured database. A partially interrupted run is
safe to repeat, but search may be incomplete until it finishes. Orphaned search
terms for deleted masters are filtered from results, but are not yet cleaned up.

The canonical English and Marathi names come from the Product Master database.
`catalog-aliases.v1.json` is now generated by `npm run build:catalog` from the
5,031-product source in `apps/web/data/catalog/` (see its README). It holds the
Hindi name and romanized/regional aliases for each code. Load new master rows
first with
`npm run import:product-master --workspace=@gaavli/web -- --file=data/catalog/product-master.v2.json`
(dry run, then `--apply`), then re-run the index backfill above. Hindi and
Marathi names have not been checked by a native speaker yet.

`npm run test:catalog-search --workspace=@gaavli/web` uses a randomly named
isolated database on the configured MongoDB server and removes it afterwards.
It checks the supplied multilingual examples, one-edit matching, inactive
filtering and `IXSCAN` plans on a small fixture. It is not a load benchmark.

Before this directory can be considered complete: design catalog categories,
variants, units, source attribution and translation review; provide a reviewed
catalog and admin import/request workflows; maintain search terms atomically
with catalog changes; add pagination and incremental local indexed storage with
transactional sync and tombstones; preserve legacy queued writes while enforcing
selection and allowed units for new ones; add broader catalog cache invalidation,
mobile and API integration tests, migration and rollout controls; and benchmark
realistic 50,000-product datasets with query
plans, concurrency, payloads, memory, percentiles and hardware details.
